## BUG B — `import torch` (any attr-proxy module) silently zeroes all kills  [CRITICAL]

**Symptom:** `detective converge` on ANY function whose module imports `torch` reports
`Incomplete · 0/N killed` — silently (no refusal), even with correct distinguishing `--input`.
Every real pabkit module imports torch, so Detective is blind on the whole codebase and says so
in no way the user can detect.

**Isolation (identical function, only the top import differs):**
- `count_below` (scalar): 14/14 clean → **0/14** with `import torch`
- `categorize` (tuple): 8/8 clean → **0/8** with `import torch`
- `import numpy` → fine (34/61). Budget increases do NOT help (distinguishes it from BUG A).
- `_outcome` observation works with torch; thread test-runner works with torch; tracing works.

**Root cause:** `Wesker/engine.py:4515`, in `_patch_module_qualified` (scans `sys.modules`):
```python
try:
    obj = getattr(mod, func_name, None)   # 4512 — inside try
except Exception:
    continue
code = getattr(obj, "__code__", None)     # 4515 — OUTSIDE the try  ← crashes
```
`torch._classes` (present in sys.modules once torch is imported) has a permissive `__getattr__`
that returns a **proxy for any attribute name** — so `getattr(mod, func_name, None)` returns a
proxy, NOT None (the default never fires). Then `getattr(proxy, "__code__", None)` runs
`torch._C._get_custom_class_python_wrapper('<name>.__code__')` → `RuntimeError: Tried to
instantiate class '<name>.__code__', but it does not exist!`. That RuntimeError is not caught
(4515 is outside the 4511-4514 try), escapes `_patch_module_qualified`, escapes
`evaluate_mutant`; the enclosing loop treats an `evaluate_mutant` raise as an "un-evaluable
survivor — conservative, never inflates the kill score" → **every mutant → survivor → 0 killed.**

Consistent with: torch-specific (only torch ships attr-proxy modules), budget-immune (exception,
not timeout), observation unaffected (doesn't patch).

**Fix:** bring the `__code__` fetch inside the guarded block:
```python
try:
    obj = getattr(mod, func_name, None)
    code = getattr(obj, "__code__", None)
except Exception:
    continue
if code is None:
    continue
```
Check the sibling scans for the same shape: the class-method-owner loop below
(`_get_raw_attr`/`getattr(..., "__code__")` around 4547-4548) and any other `sys.modules`
walk that reads attrs off arbitrary modules (`_patch_mutant_into_test`, impact-map scans).
Consider a `_safe_getattr` helper used everywhere Wesker introspects foreign modules.

**Bigger question (founder call):** a crash while measuring should arguably be a *refusal*
(exit 2 / "could not measure"), not fold into a 0-kill Incomplete. Silent blindness on a whole
class of real code is the one outcome Detective says it must never produce.

# UX NOTES — greenfield author on pabkit (not bugs; friction worth smoothing)

Grounded in what a first-time author actually hits running Detective on a real ML repo.

**U1 — Silent 0-kill on an un-measurable module is the worst first impression [ties to BUG B].**
Before the fix, a torch repo (i.e. most ML repos) got `Incomplete · 0/N killed` with a confident
`DO THIS` — a green-looking "here are your gaps" that was actually total blindness. The fix
restores measurement, but the PRINCIPLE for greenfield trust: when the engine cannot measure a
module (an introspection error, an un-evaluable universe), it should REFUSE / say "could not
measure" — never emit a 0-kill that reads like a finding. A first-timer cannot tell blindness
from a clean floor. (Founder call: add a "N mutants un-evaluable" floor to the report + non-zero
disposition when the whole universe is un-evaluable.)

**U2 — The environment requirement is the #1 setup friction, and there's no `doctor`.**
Detective must run under an interpreter that has pytest AND the target's own deps (it opens a live
in-process pytest). A bare global `detective` on a torch project refuses ("could not be collected").
`regime` explains the testing regime but does NOT diagnose "you are in an env without pytest / the
project's deps — here is the venv to use." A `detective doctor` (or a regime line: "interpreter X
is missing: pytest, torch → run from the venv that has them") would turn a confusing refusal into a
one-line fix. This is the single biggest greenfield stumble.

**U3 — The "unsound" float outcome leaves the user without a next action.**
`learning_stability` → `Incomplete · 0/10 killed`, DO THIS lists inputs marked
`SUGGESTED — not written: unsound (…ULP…)`. Correct and honest, but a first-timer is stranded:
the suggested inputs are told to be unsound, and nothing says what to DO. A closing line —
"this function is only distinguishable by exact float equality (fragile); pin a tolerance/relational
property by hand, or `flag` the survivors as equivalent" — would convert a dead end into guidance.

**U4 — Writing a test that kills 0 reads as noise.** The lone synth for `learning_stability`
(`assert f(1,2) != f(2,1)`) is a true property but kills nothing (invariant under the swap
mutation). Next to `0/10 killed` it looks like the tool did nothing useful. Either don't emit a
0-kill test, or label it "characterization only — kills no mutant."

**U5 — "Proposed removals: <your own test>" can alarm.** converge/audit proposed pruning the
author's hand-written `test_class_wise_progression` as coverage-redundant (in favour of a synth
that, pre-fix, killed nothing). It IS a proposal (never auto) and says so, but a greenfield user
reads "delete your test" as hostile. Soften: "the generated suite already covers these lines +
kills; your test is redundant FOR COVERAGE — keep it if it encodes intent."

**U6 — Jargon density on first contact.** `not consulted`, `deferred-shaped`, `DOF-proxy`,
`gamma_seam (γ-bound proxy)`, `κ`, `I_solve`, `policy 5.751e8e9f4f11` appear with no first-run
glossary. Each is meaningful, but a first-timer needs a one-line gloss or a `--explain`. The
top-line verdicts (`✓ COMPLETE`, `Incomplete: N killable · M-line gap`) are excellent; the residual
vocabulary underneath is where it gets steep.

**U7 — Good UX to keep (not everything is friction):** the `DO THIS` blocks with concrete
copy-pasteable `--input`s; `regime --migrate` creating pyproject and saying exactly what it wrote;
`audit`'s "is the TEST wrong or the CODE broken? your call"; `flag`/`flag-line`'s "proof beats
judgement"; the exit-code table in `--help`. These are model command-line pedagogy.

# FOLLOW-ON: Detective caught the paper↔spec↔code inconsistencies (a headline win)

Running `audit`/`converge` on pabkit didn't just find code bugs — cross-reading the results
against the position paper (`process_makes_perfect.md`) and the formal spec
(`mathematical_formalism.md`) surfaced that the THREE layers disagree with each other:

- **`learning_curve_predictability` has two contradictory definitions.** Paper Eq. (5) is a mean
  of ABSOLUTE first-differences — which is byte-identical to Eq. (2) `S(T)` (stability), i.e. two
  named metrics collapse to one. The spec §4 defines it as mean SQUARED (`E[(R_t−R_{t-1})²]`). The
  code uses `np.var` (≈ squared). Three-way divergence.
- **`generalization_efficiency` sign.** Spec §2: `R_train − R_test`; code: `val − train` (opposite
  sign for losses). Its test fails only on float exact-equality (`0.6−0.5 ≠ 0.1`).
- **`overfitting_risk` is a no-op** — `zip(val_losses, val_losses)` self-zip: `train_losses` dead,
  gaps all 0, `overfitting_detected` can never fire. Contradicts spec Recommendation #1.

The tool designed to pin ONE function's behaviour, pointed at a repo, made the gap between what the
paper CLAIMS, what the spec DEFINES, and what the code DOES legible in a single pass. That is the
measurement/decision discipline one layer up.

## Reconciled spec — "what BOTH were trying to be" (D1–D7, for author sign-off)
- **D1 learning_stability(losses)** = mean |Δloss| over a trajectory (spec §1). Drop the repo's
  per-step relative `/(prev+eps)`.
- **D2 learning_curve_predictability(losses)** = mean (Δloss)² (spec §4, SQUARED). Resolves the
  P_learn≡S collapse: S is absolute, P_learn is squared. Distinct, both defensible.
- **D3 generalization_efficiency(train, test)** = mean(test − train) = the generalization GAP,
  ≥0 normally, LOWER is better. Corrects the spec's sign (its `train−test` is ≤0 for losses);
  matches the paper's "smaller gap = better" and the repo's convention.
- **D4 class_wise_progression** keeps the thirds (early=first-cross in first third; late=first-cross
  in last third OR never; unstable=crosses then drops). Brittle for tiny T; intent tests use T≥6.
- **D5 rule_evolution(reps)** = mean L2 of consecutive representation diffs (spec §3, raw).
  representation_similarity(a,b)=cosine. Both over plain list[float(s)] → --input-expressible.
- **D6 robustness_evolution(clean, adv)** = adv/clean ratio, peak, final, degradation from peak.
- **D7 overfitting_risk(train, val)** = gap[t]=val−train (FIX self-zip); detected when gap trends
  up AND val rose above its own minimum (spec Rec #1).

Build target: a pure, stdlib-only `pab.metrics` where every function is a total map over primitive
containers → the WHOLE surface is --input-expressible and mutation-pinnable (and SICP-clean for the
plan/parsimony pass). Intent tests derived from THIS spec, before the code — and they fail the repo
code (the Platonic intent-test property).

# DESIGN PRINCIPLE (founder framing): the CLI must be UN-SPIRAL-ABLE

The organizing lesson behind every refinement lead below. A rigorous tool's CLI must not merely
be *correct* — it must never send a user (expert OR greenfield) into a tuning-style spiral:
re-running, tweaking an input, nudging a threshold, in search of a green stamp that the current
output implies is one tweak away when it is not. Wherever a residual or a wobble appears, the
output must NAME the situation and its single clean next action, so the spiral never *begins*.
A residual that invites "try another input / run it again" when the real move is "hand-write this /
accept-equivalent / that's estimate-noise, ignore" is a UX defect even when the math is sound.

Test: would this line make me — or a first-time author — start tuning? If yes, it needs to name
the escape instead. The spiral-inducers this session actually produced:

| spiral-inducer (observed) | why it invites tuning | un-spiral-able CLI move |
|---|---|---|
| BUG B: torch → silent `0/N killed` | reads as "unpinnable — supply more --input" | REFUSE / "could not measure this module (N mutants un-evaluable)" — never a green-looking 0 |
| message-only mutant residual | prints BOTH "supply --input" AND "hand-write" for one mutant; --input loops | one line: "exception-message-only on f(<input>); --input cannot close — hand-write pytest.raises(match=...)" |
| kill-count wobble (45/64 ↔ 43/62) | looks like "my edit broke something — re-run and compare" | label the count "≈ in-process estimate; killset/proof is stable — re-running moves the count, not the verdict" |
| BUG A (my cache contamination) | 0-kill from a stale/shared-digest `.wesker` verdict → "change budget, change input" | surface when a cached or identical-body verdict is reused; make `purge` the named reset |

The through-line: the founder-call under BUG B ("a crash/blind spot while measuring should REFUSE,
not report 0") is the same principle as the message-mutant copy fix and the count-noise label —
all three are "name the state and its one escape, so no one tunes." That is the CLI's pedagogy
job, and it is what separates a tool a greenfield author trusts from one that quietly wastes their
afternoon.

# DESIGN IDEA (founder): a "pure-decision-in-impure-shell" detector (setup/lint + first-pass flag)

The single highest-leverage move for knowability this whole session — extract the pure decisions
out of impure shells so converge can reach and pin them — is one a FLUENT operator does reflexively
and a naive one never thinks of (no reps with the tool). It shouldn't require fluency. Proposal: a
lightweight static codebase pass, available as a setup/lint step AND as a flag on Detective's
first-pass toolkit (e.g. `regime --survey` / `plan --extractable` / a new `detective survey`), that
reads the repo and says, in the founder's words:

  "hey, these files hide a lot of pure functions in an impure shell. If that's your kink, cool —
   but if you pull them out, I'd actually be able to reach and pin them."

Non-judgmental, opt-in, advisory. It turns the architectural insight into a **yes/no** ("extract
this pure core? y/n") instead of tribal knowledge.

## What it would detect (static AST heuristics, no execution — cheap, first-pass)
- Functions whose PARAMS are `--input`-expressible (int/str/bool/list/dict/tuple of those) but whose
  BODY is entangled with impure calls (open/read/write, `torch.*`, `model(...)`, `np.load`,
  `plt.*`, network/subprocess) — a pure decision wearing an I/O coat.
- Functions with an impure PARAM (model/loader/ndarray/Any/callable) that nonetheless contain a
  self-contained pure sub-block over primitives (a decision computed from scalars/lists before the
  I/O) — the extractable core (e.g. repo `overfitting_risk` buried the gap-trend decision;
  `core.py` buried the whole Algorithm-1 aggregation in the stateful orchestrator; `tracking` buried
  `should_save`/`prune` in file I/O — ALL of which this reconciled build extracted by hand).
- Output per file: "N functions hold ~M lines of pinnable pure decision behind an impure boundary;
  extracting them would raise reachable/pinnable surface from X% to Y%." A priced, opt-in nudge.

## Why it fits the session's throughline
It is the un-spiral-able / knowability principle applied one level UP — before converge even runs.
Detective already tells you, per function, "this param is inexpressible so I can't reach the branch"
(the expressibility boundary). This detector says it at REPO scale, PROACTIVELY, and names the fix.
It is exactly what would have turned my manual reconciliation (read paper+repo, notice the pure
cores, extract metrics/trajectory/tracking-decisions) into a Detective-suggested yes/no — which is
the stated goal: "the task should just be a yes or no for what Detective suggests but can't confirm."

Caveat to honour the sandwich thesis: this is a STATIC ADVISORY pass (like parsimony/plan), not a
mutation profile — it proposes extractions, never performs them, and each proposed extraction is
then converged in isolation the normal way. It widens WHERE to point Detective; it does not change
what a pin means.

## FINDING — converge advises `regime --migrate` after it already wrote a runnable suite  [COLLECTED]

Once BUG C was fixed, a sibling defect stayed visible (and had *compounded* with BUG C into the
infinite spiral). On **run 1** of a from-scratch target, converge synthesizes AND writes a runnable

closable. This is the same "measured signal not re-consumed" class the function was written to kill
(its own docstring narrates a prior spiral) — surviving in the "began empty, wrote a runnable suite,
closable gap remains" case.

**Proposed fix (not yet applied — needs a design beat, and its own pin, since `converge_next_action`

# #4 BUILT — `detective survey` (the pure-in-impure detector)

A new static, opt-in advisory command (`Detective/survey.py` + wired into cli.py, `_STATIC_COMMANDS`)
that finds functions hiding a pinnable PURE decision behind an impure boundary and NAMES the
extraction. It builds on the existing `purity.py` (`world_effects`), writes nothing, and PROPOSES
never performs — each proposed extraction is then converged in isolation the normal way, so the unit
stays ONE function (sandwich thesis intact). Three dispositions, most-blocking first:
`extractable_core` (a data-object param — ndarray/Tensor/np.*/torch.* — wrapping a decision) ·
`impure_body` (expressible params, body entangled with world effects) · `trapped_by_imports` (a pure
function that does NOT itself use the heavy stack, stranded in a module whose top-level imports are
torch/jax/matplotlib/…).

**Precision is the whole game (the founder's "don't cry wolf").** Two over-flagging traps were found
and closed by running it on the dogfood set:
- A conservative annotation DENYLIST, not an allowlist: `Grid`/`Numerical` aliases, `Callable` (a HOF
  has no primitive decision to extract), and bare `Any`/`object` (too broad — `identity(x: Any)`) are
  NOT flagged. arc-dsl `dsl.py`: **0 flagged** (was 13 false positives before the fix).
- `trapped_by_imports` fires only for a function that references NONE of the heavy import's bound
  names — a function that actually uses `jnp`/`vmap`/`plt` belongs in the module, not "trapped."
  conorheins `utils.py`: **6 flagged** (was 32), and the three spot-on are exactly the extractable
  pure decisions the manual read found — `str2bool`, `initialize_meta_params`, `get_default_inits`.

**Disclosed recall bound (honest, pinned):** an UNANNOTATED param used as an object/array (GofL
`Game.update_cell`) is NOT flagged — expressibility is unknown without call-site type inference, so
the survey stays silent rather than guess. The report says so; an intent test pins the silence, so a
future change that starts flagging it is a deliberate decision, not a drift. (Same root limitation as
the `provide_sample` residual above — unannotated-param type inference is the one larger feature both
would want.)

**Pinned:** `survey_disposition` ✓ COMPLETE 8/8 and `_annotation_inexpressible` ✓ COMPLETE 5/5 (the
pure decisions), paired with `tests/test_survey_intent.py` — intent tests written from what the
detector MUST flag and MUST stay quiet on (including the recall-bound silence). ruff clean.
